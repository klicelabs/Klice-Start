R1 — ext quebra tsc --noEmit (18 erros novos)

Evidência
cd apps/extension && bun run compile → 18 erros TS2339/TS2353/TS2554/TS7006, todos em entrypoints/background.ts (ex.: Property 'onStartup' does not exist on type 'typeof runtime'). Causa raiz

Fix (onda 3)
ext agora é tipado como typeof Browser do wxt/browser — o tipo completo derivado de @types/chrome que o WXT já gera para o global browser, sem dependência nova. O .mts de teste entrou no exclude do tsconfig (convenção dos testes existentes).
Validação
tsc --noEmit → 0 erros (19/19 resolvidos, incluindo a cascata de implicit-any nos callbacks, que era efeito colateral do tipo mínimo). Builds chrome-mv3 e firefox-mv3 ✔; suíte 51 verdes (C3 segue vermelho por desenho).

Original

C3 — Esc durante o drag não torna o drop inerte (forma mais grave que a original)

Original
resetDrag limpa refs mas o drag nativo continua; o drop resolveria pelo fallback de dataTransfer e persistiria o move cancelado. Status anterior: "Muito provável".
Reprodução (loop vermelho)
zz-audit-c3-esc-drop.test.tsx, cenário B: dragstart → Esc entregue (o handler de cancelamento do hook roda: restoreSnapshot() + resetDrag(), dragRef=null confirmado via getActiveDrag()) → drop → onBackgroundDrop dispara. handleBackgroundDrop/handleItemDrop fazem dragRef.current ?? resolveDrag(e) — o fallback relê o payload e re-arma o gesto mesmo após um cancelamento observado. Cenário A (Esc não entregue, como o Chrome faz em drag nativo sem teclado) também commita.
Interpretação
O bug original era "o cancelamento não é comunicado ao drop". O loop prova a forma forte: mesmo o cancelamento que roda é ignorado pelo drop. O flag de época/gesto-cancelado proposto no fix original continua sendo o caminho — mas precisa ser checado nos handlers de drop, não só no cancel.
Limitação honesta
linkedom não entrega o ciclo nativo completo do Chrome; em navegador real o cenário A é o esperado (Esc engolido) e o B cobre plataformas/diálogos onde keydown passa. Ambos commitam no código atual.
Arquivos
src/hooks/use-grid-dnd.ts:196-215 (cancel), :412-448 (handleItemDrop), :458-468 (handleBackgroundDrop), src/lib/dnd.ts (resolveDragRef/resolveDrag).
Próxima ação
Flag de gesto (id incrementado a cada dragstart, invalidado em Esc/dragend) checada antes do resolveDrag(e) nos dois handlers de drop + clearGestureCapture() no cancel.
High (rebaixado de Critical)Resolvido parcialmente (R1 resolvido na onda 3)

Novos achados (2ª passada)

HighNovo — confirmado por rastreio

N1 — Background grava o setup sem carimbo de geração: pós-reset, saves do contexto/atalho ressuscitam dado morto

Mecanismo
beginReset() incrementa __perchResetGeneration; loads rejeitam envelopes com geração menor (persistedGeneration < resetGeneration → null), e a ausência do carimbo parseia como 0. writeSetup do background (background.ts:38) serializa { state } sem PERSIST_GENERATION_KEY e sem ler a geração corrente. Depois de um reset, o próximo save do menu de contexto/atalho lê o setup antigo (ou default), grava, mostra badge "✓" — mas o envelope sem carimbo é descartado por toda hidratação (0 < 1) e ignorado pelo cross-tab sync dos outras abas (use-cross-tab-sync rejeita geração < corrente). Resultado: quick-save pós-reset apaga silenciosamente — a UI do background confirma, o dado nunca aparece e ainda contamina o storage com um estado paralelo morto.
Combinação
M13 (aba morta) + M14 (fora do protocolo) + este caminho = três escritores, um sem participação no protocolo. Nuvem de risco única.
Próxima ação
writeSetup deve ler a geração corrente e gravá-la no envelope; idealmente rotear pelo mesmo adapter do newtab.
MediumNovo — confirmado por rastreio

N2 — Pasta placeholder do pending-save nunca resolvida; rollback a deixa vazia e "Nova Pasta" pode reusar id órfão

Mecanismo
No fluxo pendente do popup, addFolder(name, parentId) cria a pasta com o nome digitado e o card nela. Se o usuário fechar sem salvar, nada limpa (a pasta fica vazia e visível). Se o save falha, o rollback faz deleteFolder(createdFolderId) — a pasta some, mas o id já circulado pode ser re-atribuído por uid() num save seguinte (o store não guarda tombstones de id).
Por que importa
Estados intermediários visíveis + reuso de id quebram a premissa de identidade estável do histórico e do DnD.
Decisão ligada
NPD-2 — decidida: pasta somente no commit (ver Decisões).
MediumNovo (resíduo de C2)

D2 — Valor corrupto no storage: sessão degradada em silêncio, sem quarentena

Sintoma real
Hidratação rejeitada é absorvida pelo zustand; app roda com defaults; hasHydrated=false desliga Back/Forward para sempre naquela aba; o valor ruim permanece no storage e nenhuma UI reporta.
Próxima ação
Catch simétrico + quarentena + reuso do canal de reportPersistenceError.
MediumNovo (substitui L7)

D4 — Drop cross-window (fallback dataTransfer) commita sem protocolo de intenção

Mecanismo
resolveDrag aceita payload de outra janela (drag para a janela do newtab a partir de outra aba/janela). Os handlers de drop tratam como gesto local: commita onBackgroundDrop/onDropOnFolder no container atual sem capture de gesto consistente — histórico pode não registrar ou registrar errado.
Relação
É a forma real do problema que o L7 original apontou de forma imprecisa.
Decisão ligada
NPD-4 — decidida: rejeitar cross-window drops sem contexto de gesto confiável (ver Decisões).
